# RF-102 Intake — Workspace Application Ports and Use Cases

**Task:** `RF-102 — Extract workspace application ports and use cases`

**Date:** 2026-07-30

**Status:** `COMPLETE` — architecture and formal task acceptance passed on 2026-07-30

## Goal

Create the runtime-neutral `@fishmark/workspace-application` package so workspace business workflows are independently testable without Electron or React. Main IPC handlers must become adapters that identify the caller, invoke an explicit use case, and map the result; they must not own workspace workflow decisions.

## In scope

- Add the production `packages/workspace-application` package with one public entry.
- Define only the file, identity, dialog, watcher, lifecycle, and coordination ports consumed by RF-102, without importing Electron, React, DOM, Node APIs, shared IPC DTOs, or CodeMirror.
- Extract application use cases for current document edits, save, and tab/window close workflows.
- Move current create/open/activate/reorder/move/detach/reload/watch/save/close orchestration behind the workspace application facade. RF-101 introduced several main-local application modules after the original RF-102 file list was written; leaving them beside the new package would create a second application layer.
- Preserve the RF-101 canonical `WorkspaceState`, file-identity ownership, operation ordering, close leases, and typed stale/conflict/cancellation results.
- Convert `main.ts` to dependency construction, native adapter wiring, IPC registration, and result projection only.
- Hard-delete `src/main/workspace-application.ts`, `src/main/workspace-close-coordinator.ts`, every migrated `src/main/workspace-*-application.ts` business implementation, their obsolete tests/helpers, and every superseded import after cutover.
- Activate the workspace-application architecture boundary and add focused package tests and source guards.

## Out of scope

- Persistent `TextBuffer` infrastructure and session edit revisions beyond the current RF-101 model (`RF-201`).
- Revisioned incremental edit IPC and removal of full-draft synchronization (`RF-202`–`RF-204`).
- New safe-save, recovery-journal persistence, external-conflict, or watcher semantics (`RF-301`–`RF-304`).
- Recursive Markdown parsing, structure caching, semantic editing commands, CodeMirror adapter work, or visible editing behavior changes.
- Moving Electron-specific window registration, request brokers, filesystem/dialog/watcher implementations, or IPC DTO mapping into the runtime-neutral package.
- Compatibility facades, duplicate application owners, speculative infrastructure implementations, or behavior changes unrelated to application extraction.

## Acceptance

- `@fishmark/workspace-application` depends only on `@fishmark/workspace-domain` and declared runtime-neutral ports.
- Its public entry is the only consumer import path; package-internal imports from outside are rejected.
- Current create/open/activate/move/reload/edit/save/close behavior is preserved, including exact owner/revision checks and RF-101 transaction ordering.
- Success, cancellation, stale/conflict, and error outcomes remain explicit and typed; errors are not collapsed into false success.
- `main.ts` contains composition and IPC/native adapter wiring, not workspace business decisions.
- All superseded main-local workspace application/coordinator paths, tests, helpers, imports, and compatibility symbols are absent; one production application layer remains.
- No Electron, React, DOM, Node, shared IPC DTO, or CodeMirror import exists in the new package.
- No user-visible Markdown, cursor, IME, undo/redo, autosave, or round-trip behavior regresses.

## Risks

- Splitting only file locations while leaving decisions in `main.ts` would create a cosmetic package and fail the task outcome.
- Moving Electron sender/window types into ports would make the application layer infrastructure-dependent.
- Replacing exact RF-101 owner/revision/lease checks with generic callbacks could reopen data-loss races.
- A forwarding wrapper at either the old main path or new package path would violate the hard-cutover requirement.
- Build order and runtime package resolution must include both workspace packages; source aliases alone are insufficient for Electron output.
