## 切片十三（2026-09-19）：更正切片十二的错误结论

**切片十二说"多余换行由 `computeNormalizedOrderedListDocument` 插入"是错的。** 我用单元级探针直接验证了归一化器：对规划器输出 `1. Alpha\n2. Beta\n2. Gamma`，把 5 个候选 `changedRanges`（`8→15`、`8→8`、`11→15`、`12→15`、`8→12`）**逐个**传给 `computeNormalizedOrderedListDocument`，**全部返回期望的 `1. Alpha\n2. Beta\n3. Gamma`**。所以归一化器不可能是插入换行的组件。

### 对"关闭归一化就正常"的正确解释

把 `shouldNormalizeOrderedLists` 置为 `false` 会让 `markdown.ts` 的事务过滤器在

```ts
if (!shouldNormalizeOrderedLists && !shouldNormalizeHiddenSelection && !shouldNormalizeStructuralNavigation) {
  return transaction;      // ← 这里提前返回
}
```

**提前返回**，从而跳过了**它之后**的整段代码——也就是隐藏 marker 选区归一化与结构导航归一化分支（`markdown.ts:1099` 起）以及 follow-up 事务的构造。因此切片十二的观察只能证明"问题出在 1057 行之后"，**不能证明是归一化器**。

### 一个有意思的推断

关闭归一化时，隐藏/结构导航分支**反而第一次真正运行**（因为没提前返回），而那次产出是正确的。这意味着问题更可能出在**归一化开启时的组合路径**上：归一化产生 follow-up 事务（`sequential: true`），而语义 Enter 事务叠加这些 follow-up 后，文档在**两次应用之间**的形状让第二个 follow-up 或渲染器的帧合并产生了额外换行。

### 下一轮方案（更精确）

1. 在过滤器出口处打印 `effectiveSource`、`followUpTransactions` 的数量与内容，以及最终返回的 `TransactionSpec[]`——直接看是谁在最终结果里写入了换行。
2. 重点怀疑：`followUpTransactions` 与语义事务的 `sequential` 叠加，以及 `code-editor.ts` 的 `onDocumentChangeFrame`/`requestAnimationFrame` 帧合并对同一批事务的二次处理。
3. 若确认是组合路径问题，考虑让语义事务承担"自己已经是最终文本"的语义（例如加注解跳过这些后处理），或把相应规则迁进 `@fishmark/editor-model`。

## 切片十二（2026-09-19）：责任组件已确认 —— `computeNormalizedOrderedListDocument`（**结论已被切片十三更正**）

执行了切片十一设计的判别实验（全部改动已还原）：

**在 `markdown.ts` 里把 `shouldNormalizeOrderedLists` 强制为 `false`，只切 Enter，跑单个拆分用例：**

| 归一化 | 实际产出 |
| --- | --- |
| 关闭 | `1. Alpha\n2. Beta\n2. Gamma` |
| 开启（真实） | `1. Alpha\n2. \nBeta\n3. Gamma` |
| 期望 | `1. Alpha\n2. Beta\n3. Gamma` |

结论明确：**关闭归一化后，产出与规划器中间结果逐字一致，多余换行消失**。所以责任组件是 `packages/editor-core/src/commands/list-edits.ts` 的 `computeNormalizedOrderedListDocument`——它本应只把第二个 `2.` 改成 `3.`，却在 `2. ` 之后**插入了换行**。

### 已定位到的可疑代码路径

`computeNormalizedOrderedListDocument` 对"单范围变更"走 `computeChangedRangeOrderedListNormalization`（`list-edits.ts:783`）：

- `findPotentialChangedListRange` 由 `changedRange` 反推候选块范围；
- 然后在**候选块子串**上重新解析并调用 `normalizeOrderedListBlock`；
- 最后用 `baseOffset = candidateRange.from + targetBlock.startOffset` 把内部变更映射回全文偏移。

语义路径传入的 `changedRanges` 来自 `readTransactionChangedRanges`（取 `fromB/toB`，即新文档坐标）。规划器插入的是 `"\n2. "`（7 个字符），旧路径插入的是别的形状，因此**同一套偏移反推在两条路径上得到不同结果**是最可能的原因。下一轮应在 `computeChangedRangeOrderedListNormalization` 上加临时日志，打印 `candidateRange`、`changedFrom/To`、`targetBlock` 范围与最终 `changes`，与真实产出对照。

2. 若确认是偏移映射 bug，修 `list-edits.ts`（同时跑 `code-editor.test.ts` 与 `markdown.test.ts`，因为旧路径也在用同一个归一化器）。

## 切片八：Enter 列表升级族首项修复成功（22 → 21）

按切片七的指引改 **`planListItemEnter`**，这次命中并取得了**真实语料上的净收益**。

**关键根因（前两轮失败的原因）**：`isEmptyItem` 由 `leftContent = source.slice(line.contentStartOffset, offset)` 计算，当光标**正好在内容起点**时它恒为 `true`。所以我此前写的 `!isEmptyItem && offset === line.contentStartOffset && …` 守卫**永远为假**——这解释了为什么改动完全不生效。正确做法是改用"光标右侧是否还有内容"来判断：

const hasContent = context.source.slice(offset, line.contentEndOffset).trim().length > 0;

## 切片七：Enter 升级族的真正入口被定位（尝试未通过，已回滚）
