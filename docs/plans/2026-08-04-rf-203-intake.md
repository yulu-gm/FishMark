# RF-203 Intake — Renderer Workspace Client and Pending Edit Queue

**Task:** `RF-203 — Renderer workspace client and pending edit queue`

**Date:** 2026-08-04

**Status:** `IN_PROGRESS`

## Goal

Make CodeMirror remain the immediate, optimistic editing surface while main remains the only
canonical document owner. Renderer edits must travel as ordered, revisioned `DocumentTextChange`
batches, survive delayed acknowledgements and conflicts without losing local text, and expose real
flush barriers to every existing save and ownership-changing workflow.

## Architectural decision

- Add one narrow, non-React workspace edit client and one pure pending-edit queue. Inject the client
  into the existing `WorkspaceRendererApplication`; do not create a parallel hook-owned store or
  coordinator.
- Observe CodeMirror `ViewUpdate.changes` in the renderer adapter. Compose same-frame
  `ChangeSet`s there, then cross the application boundary only as repository-owned
  `DocumentTextChange[]`; no CodeMirror type may enter the queue.
- The production editor path switches to revisioned apply/flush in RF-203. The old full-draft
  channel remains compiled only as explicit RF-204 deletion debt and must never run for the same
  edit as the new client.
- Create one random client identity per `WorkspaceEditClient` lifetime, reuse it across that client's
  tabs, and never persist or reuse it after renderer reload. Each tab starts its own sequence at 1.
  This prevents a new renderer from resetting a reused identity to sequence 1 and having real edits
  misclassified as duplicates. Old renderer identities and late results are retired locally; main's
  idempotence tombstones remain session-owned until the document session closes.
- Normal acknowledgements and projection events update metadata only and never dispatch a
  CodeMirror transaction. Canonical replacement is reserved for conflict/recovery boundaries.

## In scope

- Create `src/renderer/application/pending-edit-queue.ts` and focused tests.
- Create `src/renderer/application/workspace-edit-client.ts` and focused tests. RF-801 retains the
  broader `workspace-client.ts` name for the future complete workspace store/command gateway.
- Serialize `ViewUpdate.changes`, including sequential editor transactions, Unicode/UTF-16 and
  multi-range edits, without changing undo grouping, selection or semantic command behavior.
- Compose edits per animation frame. A normal barrier synchronously seals the current frame, but an
  active IME composition uses an asynchronous composition-aware seal: freeze the destructive command,
  wait until CodeMirror observes the final post-`compositionend` document update, then seal and set
  read-only. Destroy/unload that cannot wait must retain exact view text as recovery payload.
- Keep at most one apply request in flight per tab; retain every sealed queued/in-flight batch until
  an exact acknowledgement. The CodeMirror adapter is the only frame bucket owner and retains an
  unsealed frame until it emits it to the client. Retry transport failures with the same sequence.
- Implement per-tab and all-tab `flushEdits` cutoffs for open/create, save/autosave, switch,
  detach-to-new-window, reload, tab close and window close. Reorder remains non-destructive and does
  not require a flush.
- Keep transport baseline `{ acknowledgedText, acknowledgedTextRevision }` atomic and separate from
  UI-only observed projection metadata. Projection delivery never advances text baseline or acts as
  an edit acknowledgement.
- On revision conflict, conservatively rebase provably non-overlapping local edits onto canonical
  text. Overlap, same-point ambiguity, non-unique mapping, protocol desynchronization or unsafe IME
  timing must preserve the exact local text in an untitled recovery tab and restore the original tab
  to canonical text.
- Derive renderer dirty state from observed canonical dirty metadata plus a non-empty local pending
  queue/recovery payload, without changing the transport text baseline.
- Extend `WorkspaceRendererApplication` and its tests even though the original roadmap file list
  omitted them; it is the existing workflow owner and the only correct place to bind barriers.

## Out of scope

- Deleting `UPDATE_WORKSPACE_TAB_DRAFT_CHANNEL`, `WorkspaceDraftOutbox`, snapshot-preservation code,
  old bridge mocks or retired full-draft symbols (`RF-204`). They may remain dormant only; no new
  fallback or feature-flag routing is allowed.
- Adding a new cross-existing-window move UI. The current product path is detach-to-new-window; all
  existing renderer ownership-transfer callers are covered, but RF-203 will not claim a nonexistent
  UI scenario.
- Main save/recovery redesign, recovery journals or external-conflict ownership (`RF-301`–`RF-304`).
- Parser, recursive Markdown model, semantic command or document-cache work (`RF-401+`).
- Performance-budget claims (`RF-901`).

## Required state model

Each tab queue owns one atomic transport baseline
`{ acknowledgedText, acknowledgedTextRevision }`, separate UI-only
`{ observedRevision, observedSavedRevision, observedIsDirty }`, local optimistic text, the current
frame bucket, ordered unsent batches, at most one in-flight batch, the next client sequence, and a
lifecycle generation. Results are admitted only for the exact tab, generation and sequence.

- `applied`: retire the exact batch only when revision equals `baseRevision + 1`, then advance the
  atomic baseline to its known result text/revision.
- `duplicate`: retire the exact batch to its known result text/`baseRevision + 1`; treat the response's
  possibly newer current revision as observed UI metadata only.
- `revision-conflict`: stop the pump, retain every local change, run conservative three-way rebase,
  and retry the conflicting sequence against `canonicalRevision`; otherwise enter recovery.
- `sequence-gap`: resend the retained `expectedSequence` only when it exists; otherwise fail closed
  into recovery rather than inventing or dropping a command.
- typed error / transport failure: keep all pending data; `flushEdits` rejects and destructive
  workflow does not proceed.
- projection: update monotonic observed revision/save metadata only; never retires a pending batch or
  advances acknowledged text/revision.

Remote/canonical/recovery editor transactions carry one repository-owned internal-origin annotation;
the CodeMirror observer ignores only that annotation. Programmatic semantic editing commands remain
observable local edits.

## Acceptance

- Every production CodeMirror document change produces exact original-base `DocumentTextChange[]`
  and is sent once through the revisioned client, not through both transports.
- Same-frame batching does not alter CodeMirror transactions, undo grouping, cursor/selection,
  Enter, Backspace, nested list/blockquote behavior or IME composition.
- Delayed, duplicate and out-of-order acknowledgements cannot lose, duplicate or reorder local text.
- Every existing destructive/save barrier seals the current frame and waits through its exact
  sequence cutoff; an active IME composition first awaits its final document checkpoint.
- Successful/duplicate acknowledgements and projections do not replace the editor document or carry
  full content.
- Non-overlapping conflicts rebase deterministically. Before canonical replacement, ambiguous
  conflicts freeze the old queue and retain exact local text as a recovery payload; the old queue is
  retired only after a recovery tab acknowledges that exact text.
- Dirty UI equals observed canonical dirty metadata or local pending/recovery work; an
  acknowledgement alone cannot show clean while later edits remain pending.
- Old editor identity, late RAF callback or apply result after switch/detach/dispose has no effect on
  the new binding. A late projection may update monotonic observed UI metadata only; it cannot change
  acknowledged text/revision or retire a batch.
- The current 121-case editing behavior baseline remains unchanged with zero unexpected or not-run
  targets.

## Primary risks

- Concatenating transaction changes from different document bases corrupts offsets; frame batching
  must compose `ChangeSet`s before serialization.
- Reading a flush cutoff before synchronously sealing the current RAF bucket can lose the final
  keystroke, especially in background windows.
- Running full-draft and revisioned transports for one edit advances canonical revision twice or
  creates guaranteed conflicts.
- Applying normal acknowledgements as editor replacements destroys history, selection and IME.
- Conflict recovery without stable baseline/local text can silently drop nested Markdown structure;
  ambiguous mapping must prefer an exact recovery tab.
