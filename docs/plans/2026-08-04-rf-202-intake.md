# RF-202 Intake — Shared Edit Contract and Main Handler

**Task:** `RF-202 — Shared edit contract and main handler`

**Date:** 2026-08-04

**Status:** `COMPLETE` — formal task acceptance `PASS` on 2026-08-04.

## Goal

Expose RF-201 revisioned document edit batches through a serializable, sender-validated Electron
bridge. Normal acknowledgements and projection events must remain metadata-only; a full canonical
Markdown string may cross the boundary only for explicit revision-conflict recovery.

## In scope

- Add repository-owned shared DTOs and channel/event constants for apply, flush, and document
  projection subscription.
- Add revision metadata to the canonical workspace document snapshot used for initial renderer
  hydration.
- Add a workspace-domain/application entry that applies edit batches to the sender-owned tab
  without materializing full text on successful or duplicate acknowledgements.
- Serialize apply and flush through the existing per-tab operation coordinator.
- Add a focused preload product API module and a focused main IPC registration module.
- Validate unknown IPC payload shape, client identity, safe-integer revisions/sequences/positions,
  sender window, tab ownership, and canonical change bounds before mutation.
- Expose duplicate retries as explicit idempotent acknowledgements; expose revision conflict with
  canonical text; map gaps, malformed input, stale ownership, and overflow to typed results.
- Publish metadata-only document projection events to the owning renderer after successful or
  duplicate acknowledgement.

## Out of scope

- Renderer CodeMirror transaction serialization, animation-frame batching, pending queues,
  conflict rebase, recovery tabs, or client lifecycle retirement (`RF-203`).
- Deleting `UPDATE_WORKSPACE_TAB_DRAFT_CHANNEL`, renderer draft synchronization, or snapshot
  preservation (`RF-204`).
- Save/autosave/reload/move/detach/close cutover to renderer `flushEdits()` barriers (`RF-203` and
  `RF-204`).
- Parser, Markdown semantic commands, cursor/IME behavior, document structure caches, or measured
  performance budgets.

- Modify `src/shared/product-bridge.ts` and `src/shared/workspace.ts`.

- Extend `packages/workspace-application` with serialized apply/flush use cases while retaining the

- Update architecture/source guards, public documentation, RF roadmap/progress, and the execution
  handoff.

## Acceptance

- Shared contracts are structured-clone-safe and contain no Electron, CodeMirror, domain, or
  application types.
- Production handlers derive the expected window from `event.sender`; renderer input cannot select
  an owner window or mutate a tab after ownership changes.
- Valid non-empty changes cross preload/main/application/domain and advance exactly one canonical
  revision.
- Duplicate sequence retry is explicitly and idempotently acknowledged; sequence gaps and invalid
  payloads are typed results; stale revisions return exact canonical revision/text without dropping
  local input.
- Successful and duplicate normal responses/events contain no full Markdown content.
- Apply and flush share one per-tab serialization boundary.
- The old full-draft channel remains exactly as RF-204 retirement debt, with no second document
  owner or feature-flag routing.
- Renderer/preload/main security boundaries, Markdown round-trip, current edit UX, save flows, and
  formal behavior baseline remain unchanged.

## Risks

- Sending canonical text on every acknowledgement would erase the long-document benefit.
- Registering handlers directly against domain state would bypass application ownership and queue
  semantics.
- A flush method outside the same coordinator would be a cosmetic barrier and could race edits.
- Accepting renderer-provided window IDs would allow stale or foreign renderers to mutate tabs.
- Treating duplicate, gap, and conflict as the same error could either replay edits or silently lose
  input.
- Prematurely removing the full-draft path would break the current renderer before RF-203 exists.
