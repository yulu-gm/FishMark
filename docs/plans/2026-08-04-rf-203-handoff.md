# RF-203 Execution Handoff — Renderer Workspace Client and Pending Edit Queue

**Task:** `RF-203 — Renderer workspace client and pending edit queue`

**Date:** 2026-08-04 (intake accepted); implementation and formal acceptance completed 2026-08-13

**Status:** `COMPLETE` — independent specification, quality, architecture review, and formal task acceptance all passed.

## What changed

- Created a pure, runtime-neutral renderer pending edit queue
  (`src/renderer/application/pending-edit-queue.ts`) that owns, per tab, one atomic
  transport baseline `{ acknowledgedText, acknowledgedTextRevision }`, separate UI-only
  observed metadata `{ observedRevision, observedSavedRevision, observedIsDirty }`, the
  optimistic local text, ordered unsent batches, at most one in-flight batch, the next
  client sequence, and a lifecycle generation. It implements hydrate/enqueue/begin-send/
  admit-result/observe-projection/rebase/retire/retry-transport/recovery transitions and a
  conservative three-way rebase for provably non-overlapping local edits.
- Created the `WorkspaceEditClient` (`src/renderer/application/workspace-edit-client.ts`)
  that owns one random client identity per client lifetime (never reused across renderer
  reloads), per-tab sequence high-watermarks, composition-aware and plain edit barriers
  (`acquireTabFlushBarrier` / `acquireAllFlushBarriers`), two-phase conflict preparation/
  commit with claim tokens, typed discard-to-recovery retention, ABA epoch fences,
  exactly-once dispose/cancel semantics, and all-tab failure cleanup.
- Extended the CodeMirror adapter (`src/renderer/code-editor.ts`) with a single RAF frame
  bucket that composes same-frame `ChangeSet`s into repository-owned
  `DocumentTextChange[]` frames, a composition-aware seal (`sealForBarrier`) that waits for
  the final post-`compositionend` document checkpoint before freezing a destructive
  command, an `internalDocumentTransaction` annotation that the update observer ignores,
  and identity-fenced `applyRemoteDocumentPatch` / `restoreCanonicalDocument` remote
  transactions (no-history + internal-origin only inside the remote patch path).
- Hard-switched the production editor path to the revisioned transport:
  - `WorkspaceShell` / `App` / `useEditorWorkflowController` wire
    `onDocumentChangeFrame`, `onDiscardedDocumentText`, `onPendingDocumentChangesChange`,
    `onEditorBarrierChange`, `onEditorRemotePatchChange`, `onEditorCanonicalRestoreChange`,
    `onEditorTransitionApplied` and `onLoadRevisionApplied`; production `onChange` is no
    longer wired (legacy full-draft channel stays compiled only as explicit RF-204 debt and
    cannot run for the same edit as the new client).
  - `WorkspaceRendererApplication` enters incremental mode at pending frame admission
    (before the first RAF frame), so a pre-frame workflow can never recreate a full draft;
    legacy capture/drain/outbox paths early-return in incremental mode and remain only for
    old non-CodeMirror callers (gated by `incrementalEditingActive`).
  - Save/autosave/close/detach/window-close/export use real revisioned barriers through the
    same per-tab coordinator; `sealForBarrier` returns an immutable `{ identity, text }`
    cutoff snapshot that export consumes so a tail typed while a barrier waits can never be
    exported outside the checkpoint.
  - A non-React `WorkspaceRendererApplication` is the only production owner of the edit
    client; React hooks are presentation/binding only.
- Conflict/recovery: on `revision-conflict` the queue stops pumping, retains every local
  change, and either rebases conservatively or freezes the queue and retains the exact
  local text as a recovery payload; recovery tabs are created with a private IPC path (no
  source drain, no recursive coordinator), hydrated at revision 0 with exact incremental
  payloads, and the old queue retires only after the recovery tab acknowledges that exact
  text. A `recovering` editor transition freezes the source editor (seal + CAS +
  read-only) before recovery creation; late payloads atomically update the durable
  recovery record.
- Autosave/editor tests were migrated from legacy `updateWorkspaceTabDraft` mocks to real
  revisioned apply/flush/barrier facts (`app.autosave.test.ts`, `code-editor.test.ts`,
  `code-editor-view.test.tsx`, `useEditorApplicationController.test.tsx`,
  `workspace-renderer-application.test.ts`).
- Architecture guard updates in `src/main/editor-foundation-architecture.test.ts`:
  - The old `Transaction.addToHistory.of(false)` absence assertion was replaced with the
    RF-203 canonical contract: the only history-suppressing transaction is the
    repository-owned internal-origin remote patch (paired with
    `internalDocumentTransaction.of(true)` inside `applyRemoteDocumentPatch`, exactly one
    occurrence), and the update observer ignores exactly that annotation.
  - Added a runtime-neutrality guard for `src/renderer/application/*`: the queue and
    client may import only repository-owned shared DTOs and each other — no CodeMirror,
    React, Node, Electron, main, preload, or package imports.
  - The real-repository manifest acceptance test gained a 30 s timeout (whole-repo scan
    under full-suite parallel load).
- Independent quality-review closure (2026-08-13): the review's Critical C1 — non-conflict
  recovery sources (adapter discard, invalid frame, missing sequence) were captured but
  never materialized, so `getRecoveryPendingOutcome` permanently blocked window close —
  was fixed by scheduling automatic recovery materialization for every `recovery-required`
  outcome in `observeEditClientState` (new `scheduleRecoveryMaterialization`), exactly like
  the conflict path. `WorkspaceRendererApplication` now owns a
  `recoveryMaterializationScheduled` set with dispose cleanup and coordinator-scoped
  materialization; duplicate discards do not double-create. Three existing tests that
  assumed manual `retryRecovery` were updated to the automatic-materialization behavior,
  and two new regression tests prove a non-conflict adapter recovery materializes and the
  window closes, plus no double-materialization. The review's Important items (apply/flush
  port timeouts, blocked-queue UI retry, dormant full-draft tests still driven by old
  tests) are recorded as RF-204-deferred robustness/cleanup work; the quality reviewer's
  Minor items were assessed and are documented in the deferred-risk section below.

## Manual acceptance

1. Launch the development editor, open/create a Markdown tab, and type nested list and
   blockquote content; verify typing stays immediate, Enter/Backspace/Tab and IME behave as
   before, and the document content is sent as ordered revisioned edits (observe
   `window.fishmark.onDocumentProjection` receives metadata-only events).
2. Type while the renderer network is artificially delayed (or while a barrier is held):
   verify the editor remains responsive and optimistic, the dirty indicator stays derived
   from pending work, and no keystroke is lost.
3. Trigger a save while typing; verify the save barrier seals the current frame and the
   saved file contains exactly the checkpointed text, while later keystrokes stay pending
   and dirty.
4. Simulate a revision conflict (e.g., external edit + reload while pending edits exist);
   verify unambiguous local edits rebase onto canonical text, and ambiguous edits preserve
   the exact local text in a recovery tab with the original tab restored to canonical text.
5. Detach a tab to a new window while edits are pending; verify the pending edits move with
   the tab and no full-draft fallback path fires.
6. Verify the legacy full-draft channel (`updateWorkspaceTabDraft`) is never invoked for
   edits made through the production editor; it exists only as dormant RF-204 debt.

## Known risks and explicitly deferred work

- The full-draft channel (`UPDATE_WORKSPACE_TAB_DRAFT_CHANNEL`,
  `updateWorkspaceTabDraft`, `WorkspaceDraftOutbox`, snapshot-preservation code and the
  dormant legacy capture/drain paths) is intentionally retained only as explicit RF-204
  deletion debt. No feature flag routes new edits to it; RF-204 must delete it without
  leaving a compatibility route or second owner.
- Independent quality-review findings assessed as RF-204-deferred robustness/cleanup:
  - The apply and flush transport ports race only against retire/cancel, with no deadline;
    a hung main IPC would keep save/close/export pending indefinitely. A bounded transport
    deadline with fail-closed retention belongs in RF-204's transport hardening.
  - A transport-failure-exhausted `blocked` queue has no production UI retry entry
    (`retryRecovery` exists but is not exposed); data is retained fail-closed, and the UI
    recovery entry is a product decision for RF-204.
  - Old tests still drive the dormant full-draft bridge for legacy-only scenarios; those
    mocks are RF-204 deletion debt, and production code cannot reach the full-draft path.
  - Minor review items (metadata-only projection rejected still returning true, stale seal
    waiter cleanup, frame-rejection discard diagnostics, canonical dirty contradiction
    throwing, module-size splitting, retired-entry activeSend cleanup) were assessed; none
    blocks RF-203 acceptance, and the two state-hygiene items (waiter cleanup, activeSend
    cleanup) are candidates for RF-204 hardening.
- RF-301+ still own main save/recovery redesign, recovery journals, per-document watch
  registry and external-conflict ownership.
- The editor-behavior paint/focus settling flake documented in RF-101/RF-102 acceptance
  remains; it is visibility-only and resolves on exclusive rerun. Runner hardening is
  deferred (not part of RF-203).
- The existing 8 lint warnings and the Vite large-chunk advisory are unchanged. No
  performance budget is claimed by RF-203.
