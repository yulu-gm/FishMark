# RF-002 Architecture and Performance Guards Intake

Date: 2026-07-14
Task: RF-002
Status: IN_PROGRESS

## Goal

Establish fail-closed, machine-readable architecture guards and a comparable current performance baseline before the editor foundation moves. RF-002 freezes evidence; it does not implement the target workspace domain, recursive parser, incremental cache, semantic editor model, or CodeMirror adapter.

The task must make three claims executable:

1. a new dependency edge, document-parse entry point, compatibility path, or retired symbol cannot appear without an explicit lifecycle rule;
2. the RF performance baseline always measures the same committed 20,000-line Markdown source;
3. open, edit, selection, and derived-state reports expose real current counters, including honest zero values and fallback reasons for capabilities that do not exist yet.

No user-visible editing behavior changes in RF-002.

## In scope

### 1. Machine-readable architecture guard

- Add one versioned guard manifest as the canonical source for active package/import rules, declared target-package lifecycle, document-parse entry points, exact temporary exceptions, cutover retirements, and bundle-facing checks.
- The manifest and validator must fail closed on unknown rule kinds, duplicate IDs, invalid paths, missing retirement task IDs, stale exceptions, an existing target package without an active rule, or an empty active rule set.
- Enforce non-empty rules against boundaries that exist today:
  - `packages/markdown-engine` cannot import React, Electron, CodeMirror, `src/main`, `src/preload`, `src/renderer`, or `packages/editor-core`;
  - `packages/editor-core` cannot import React, Electron, `src/main`, `src/preload`, or `src/renderer`; its current CodeMirror dependency remains explicitly legal until the RF-601–RF-604 adapter cutover;
  - `src/renderer` cannot import implementation modules from `src/main` or `src/preload`;
  - `src/preload` cannot import implementation modules from `src/main` or `src/renderer`;
  - `src/main` cannot import implementation modules from `src/preload` or `src/renderer`;
  - cross-package consumers use public `@fishmark/*` entries rather than package-internal `src` paths, except for exact, named current exceptions with an owning retirement task.
- Record the future package names from the roadmap as `planned`, not `active`. Missing planned directories are not counted as passes. If a planned directory appears, the guard must require its rule to be activated in the same change.
- Scan static imports, re-exports, and string-literal dynamic imports. The guard does not pretend to prove runtime behavior from comments or arbitrary strings.
- Give each exact legacy exception an owner, reason, and `retireIn` RF task. Wildcard legacy allowlists are not acceptable.

### 2. Registered document-parse entry points and cutover lifecycle

- Register the current document-structure parse surfaces instead of deleting them early:
  - `parseMarkdownDocument` is the current rich document entry;
  - `parseBlockMap` is the current lean/legacy entry and is scheduled for RF-405 removal;
  - the internal `parseTopLevelBlocks` export and the modules that directly invoke micromark document parsing are explicitly accounted for under the same RF-405 cutover;
  - `parseInlineAst` is classified as an inline-range parser, not falsely counted as another full document parser.
- Reject a new public document parser, a new direct micromark document-parse module, or an unregistered entry-module export.
- Model retirement state explicitly, for example `present-until`, `forbidden`, and `removed`. Current APIs scheduled for RF-405/RF-604 stay legal only in their registered locations; RF-002 must not hard-delete or rename them.
- The same guard mechanism must let later cutover tasks append target-package rules and switch a registered symbol/path to `forbidden` without creating another architecture truth.

### 3. Deterministic RF performance fixture

- Commit `fixtures/performance/complex-20000-lines.md` as the only canonical RF long-document baseline.
- Commit a machine-readable fixture identity beside it with SHA-256, exact line count, byte/source length, newline policy, fixture schema version, and human-readable content profile.
- Read and hash the committed Markdown file before every RF baseline run. A line-count or hash mismatch fails before measuring anything.
- Use deterministic mixed Markdown that exercises headings, paragraphs, nested lists, nested blockquotes, code fences, block math, tables, footnotes/references, and ordinary blank lines while remaining exactly 20,000 lines.
- Keep `createLongMarkdownFixture()` only for existing small/legacy unit tests if still useful. It cannot feed the RF-002 baseline or become a second canonical 20,000-line source.
- Do not use `tmp/`, random data, current time, host-specific paths, or an in-memory/generated stress source as the RF baseline.

### 4. Honest current operation and counter schema

- Emit a versioned machine-readable report that distinguishes at least:
  - initial `open` / editor-ready construction;
  - ordinary `edit` and the existing structural/ordered-list edit path;
  - selection-only movement;
  - renderer derived state for outline and metrics.
- Every operation reports finite non-negative duration data for information and deterministic integer counters for:
  - `fullParse`;
  - `incrementalParseWindow`;
  - `cacheHit`;
  - `invalidatedNodes`;
  - `decorationRebuild`.
- Preserve entry-point detail where it exists today, including `parseMarkdownDocument` and `parseBlockMap`, rather than collapsing all work into an unexplained total.
- Counters must come from instrumentation at the operation boundary. Tests must not hardcode an improvement that the runtime does not perform.
- Because the incremental structure cache does not yet exist, its counters are expected to be zero and must be accompanied by a stable fallback/capability reason such as `incremental-structure-cache-not-implemented`. Zero without an explanation is insufficient.
- Record the current deterministic counter expectations and capability/fallback state as the comparison baseline. Runtime duration samples remain report data, not committed CI thresholds.
- Stable gates use fixture identity, operation/counter schema, finite/non-negative/integer invariants, exact capability reasons, selection-only no-full-parse behavior, and architecture/bundle checks. RF-002 does not enforce roadmap millisecond budgets across heterogeneous CI machines.

### 5. Bundle evidence without a bundler rewrite

- Extend the existing `scripts/analyze-renderer-bundle.mjs` `--json` output instead of replacing Vite or adding a second bundle analyzer.
- Add a schema version and a deterministic, sorted architecture/bundle evidence section covering the initial static-import closure, lazy requirements, source groups, applied rule/check IDs, actual values, limits, and PASS/FAIL status.
- Keep the existing first-editor-load closure model. A sourcemap build emits versioned, hash-bound bundle provenance for every chunk. `moduleIds` are the source-group authority even when Vite attests that a chunk emitted no Source Map; an expected emitted map that is missing, an unexpected map for a mapless chunk, or missing provenance must fail closed.
- Keep architecture source-import validation in the architecture guard. The bundle analyzer only proves what entered initial/lazy output and must not claim to be a TypeScript dependency graph.
- Update analyzer tests for JSON stability, fail-closed missing evidence, and non-zero exit on a failed rule.

## Out of scope

- No revisioned `DocumentSession`, workspace-domain/application/infrastructure package, edit IPC, or renderer pending queue.
- No recursive Markdown node model, full recursive parser, physical-line/prefix index, incremental parser, invalidation algorithm, or structure cache.
- No parser worker or replacement of micromark.
- No semantic Enter/Backspace/Delete/Tab/navigation refactor and no CodeMirror adapter extraction.
- No deletion of `parseBlockMap`, `parseTopLevelBlocks`, `createFishMarkMarkdownExtensions`, `packages/editor-core`, or other APIs assigned to later hard-cutover tasks.
- No attempt to fix existing parse counts, cache misses, decoration rebuilds, or long-document latency in this task.
- No new Markdown syntax, UI feature, formatting behavior, autosave behavior, selection behavior, IME behavior, or document persistence behavior.
- No Vite/bundler rewrite and no new performance framework dependency unless execution proves the existing TypeScript/Vitest/Node stack cannot express the required evidence.
- No millisecond-based CI failure threshold in RF-002; roadmap budgets remain later optimization/final-gate targets.
- No edits to `MVP_BACKLOG.md` or general `docs/progress.md`. The RF program's roadmap and progress file are the only status truth for this task.

## Acceptance

RF-002 is PASS only when all of the following are true:

1. The architecture manifest is versioned, non-empty, validated fail-closed, and is the only rule source.
2. Current markdown-engine/editor-core/main/preload/renderer boundaries are actively constrained; missing future package directories are not reported as successful packages.
3. Every current exception is exact, justified, owned by a future RF deletion task, and the test fails if the exception becomes stale or broadens.
4. Current document parse entry points remain available but are registered with roles and retirement lifecycle; an unauthorized public parser or direct micromark document parser fails the guard.
5. A synthetic forbidden import, internal cross-package import, unregistered parser entry, invalid rule, and forbidden retired symbol/path each produces a deterministic test failure.
6. `fixtures/performance/complex-20000-lines.md` is committed, exactly 20,000 lines under the declared newline policy, and matches its recorded SHA-256 before measurement.
7. The RF baseline reads that committed file directly; the existing generator is not another canonical RF input.
8. The report distinguishes open, edit, selection, outline, and metrics, and exposes all five required counters for every applicable operation.
9. Current unavailable incremental behavior is reported as zero with a real fallback/capability reason; no counter claims a cache/window/node reuse improvement that did not occur.
10. Duration fields are finite and non-negative but do not gate heterogeneous CI by milliseconds. Stable identity/schema/counter/import/bundle invariants do gate.
11. Bundle `--json` evidence is versioned, deterministic and machine-readable. Every emitted chunk is bound to final code bytes, module/import graph and an explicit Source Map state; emitted maps are integrity/structure checked, while attested mapless chunks report `NOT_EMITTED` without losing `moduleIds` authority.
12. No product editor behavior, stored Markdown, undo grouping, selection mapping, IME routing, workspace ownership, parser result, or persistence flow changes.
13. Focused verification, the full mixed-code gate, architecture acceptance, and task acceptance all pass with fresh evidence.

## Risks

- A source scanner can create false confidence if it ignores re-exports or dynamic imports; supported import forms and unsupported forms must be explicit and tested.
- An exact exception list can freeze debt if it has no retirement task or stale-entry failure.
- Treating future target packages as active would overstate the current architecture; treating absent paths as passes would hide missing work.
- Deleting legacy parse APIs now would cross into RF-405 and break the one-task rule.
- Instrumentation in a hot CodeMirror path can itself change timings or editor behavior. Counters should be test/probe scoped or have negligible disabled-path cost.
- A generated 20,000-line document can drift silently; committed bytes plus SHA-256 are mandatory.
- Millisecond thresholds are machine-sensitive. They remain informational until the later final performance task has recorded hardware and repeatable percentile sampling.
- Full parse and decoration work can be misclassified as incremental/cache work. Counter names require operation-level provenance and explicit fallback reasons.
- Bundle Source Map absence must not hide an initial dependency. Source-group authority therefore comes from hash-bound Vite `moduleIds`; Source Maps are separate optional attribution evidence whose emitted/mapless state is explicitly attested and cross-checked against disk.
- The existing renderer performance module imports an editor-core internal helper. If retained temporarily, the exact exception must be registered and assigned to the correct hard-cutover task; RF-002 must not normalize it into a permanent public API.
